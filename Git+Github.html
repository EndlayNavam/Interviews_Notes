What is Version Control? Why Git?
›

A Version Control System (VCS) tracks changes to files over time so you can recall any version later. Git is the world's most widely used distributed VCS, created by Linus Torvalds in 2005.

Problems Git Solves

  • No more project_final_v2_FINAL_new.zip — every change has proper history with a message
  • Multiple developers can work on the same codebase simultaneously without overwriting each other
  • Easily revert to any previous state if something breaks in production
  • Work on new features in isolated branches without affecting the main stable code
  • Complete audit trail: who changed what, when, and why (accountability)

Git vs GitHub

TypeSoftware / CLI toolWeb platform / service
Where it runsLocally on your machineCloud-based server
PurposeTrack changes, branching, mergingHost repos, collaborate, PRs, issues

AlternativesMercurial, SVN, PerforceGitLab, Bitbucket, Azure DevOps
🎯 Interview tip: "Git is the tool; GitHub is a hosting service that uses Git. You can use Git without GitHub (local-only repos), but you need Git to use GitHub."

Installation & Initial Configuration
› 
# Check Git version
git --version

# Set your identity (required — shows on every commit)
git config --global user.name "Your Name"
git config --global user.email "you@example.com"

# Verify all config
git config --list

# Set VS Code as default editor
git config --global core.editor "code --wait"
🎯 Interview tip: The --global flag saves config in ~/.gitconfig and applies to all repos. Without it, config is repo-specific (stored in .git/config).
02
Init Command — Creating a New Repository
›

As shown in the video: git init creates a new Git repository. It adds a hidden .git folder that stores all version history, branches, and configuration.

# 1. Initialize a new repo in the current folder
git init

# 2. Connect to a remote GitHub repository
git remote add origin <your-repository-URL>

# 3. Verify remote is correctly set
git remote -v
origin  https://github.com/user/repo.git (fetch)
origin  https://github.com/user/repo.git (push)

# 4. See current branches
git branch

# 5. Rename branch to 'main' (modern standard)
git branch -M main

# 6. First push — set upstream tracking
git push -u origin main
# After this, just 'git push' is enough
🎯 Interview tip: origin is just an alias/nickname for the remote URL. You can name it anything, but origin is the universal convention. The -u flag sets the upstream tracking reference so future pushes don't need to specify the remote name.

04
Commits — Saving Snapshots
› 
# Commit staged changes with a message
git commit -m "feat: add login page"

# Stage tracked files + commit in one step
git commit -am "fix: correct nav bar typo"

# Amend the very last commit
git commit --amend -m "corrected commit message"

# View commit history
git log
git log --oneline            # compact one-line view
git log --oneline --graph    # visual branch tree

Conventional Commit Messages

PrefixUse for
feat:A new feature
fix:A bug fix
docs:Documentation changes only
style:Formatting (no logic change)
refactor:Code restructure, no feature/fix
chore:Build process or tooling changes
🎯 Interview tip: Each commit should represent one logical change (atomic commit). This makes it easy to git revert a specific change without undoing unrelated work.
05
.gitignore — Excluding Files
›

A .gitignore file tells Git which files/folders to never track — secrets, dependencies, or build output.

# .gitignore examples
node_modules/        # npm packages — never commit
.env                 # environment variables & secrets
dist/                # build output folder
*.log                # all log files
.DS_Store            # macOS system file
*.pyc                # Python bytecode
.idea/               # JetBrains IDE config
⚠️ Never commit: API keys, passwords, .env files, or node_modules. GitHub actively scans for accidentally committed secrets and notifies service providers.

Undoing Changes — reset, revert, restore
›
CommandWhat it doesSafe for shared repos?
git restore <file>Discard working directory changes (revert to last commit)✅ Yes
git restore --staged <file>Unstage file (changes remain in working dir)✅ Yes
git reset --soft HEAD~1Undo last commit; keep changes staged⚠️ Local only
git reset HEAD~1Undo last commit; keep changes in working dir⚠️ Local only
git reset --hard HEAD~1Undo last commit AND permanently delete changes❌ Destructive
git revert <hash>Create a NEW commit that undoes a past commit — history preserved✅ Safe
🎯 Interview tip: On shared/public branches always prefer git revert over git reset. Reset rewrites history and breaks teammates' local repos. Revert adds a new "undo" commit safely.
# Undo last commit (keep changes staged)
git reset --soft HEAD~1

# Safely undo a pushed commit on shared branch
git revert <commit-hash>
git push origin main
📦
Stash — Save Work Temporarily
›

Stash is like a clipboard — save current uncommitted work, switch branches, then restore it later.

# Save changes with a description
git stash push -m "WIP: half-done login feature"

# View all stashes
git stash list
stash@{0}: WIP: half-done login feature
stash@{1}: stash on main

# Apply latest + remove from stash list
git stash pop

# Apply a specific stash (keep in list)
git stash apply stash@{1}

# Delete a specific stash
git stash drop stash@{0}

01
What are Branches?
›

As shown in the video diagram — a branch is a separate line of development. The default is main. Feature A and Feature B develop in isolation, then merge back to main (via Bug Fix branch in the diagram).

  • The main branch always has stable, production-ready code
  • New features, bug fixes, experiments live on separate branches
  • Multiple developers can work in parallel without conflicts
  • Changes are merged into main via Pull Request (PR) after code review
  • A failed branch doesn't affect main — just delete it
🎯 Interview tip: A branch in Git is simply a lightweight movable pointer to a commit. Creating a branch is nearly instant — Git doesn't copy files, it just creates a 41-byte pointer file.

git switch feature-login

git switch -c feature-login    # modern equivalent

# Rename current branch

# Delete a merged branch

# Force delete (even if unmerged)
git branch -D feature-login

# Push branch to remote
git push origin feature-login
03
Merging — Combining Branches
› 
# Step 1: Switch to the target branch (the one you merge INTO)
git checkout main

# Step 2: Merge the feature branch into main
git merge feature-login

Types of Merges

TypeWhen it happensResult
Fast-ForwardNo new commits on main since branch was createdMain pointer moves forward — clean linear history
3-Way MergeBoth branches have new diverging commitsCreates a new "merge commit" with two parents
Squash MergeMany small WIP commits on feature branchgit merge --squash — combines all into one clean commit
🎯 Interview tip: Fast-forward is only possible when there are no diverging commits. Force a merge commit even in FF cases with git merge --no-ff to preserve branch history in the log.
04
Merge Conflicts — Resolving Them
›

A conflict happens when two branches modify the same line(s) of the same file and Git cannot automatically decide which version to keep.

# Git marks the conflict like this:
<<<<<<< HEAD  (your branch)
  console.log("Hello from main");
=======
  console.log("Hello from feature");
>>>>>>> feature-login

Steps to Resolve

  • Open the conflicting file — find the <<<<<<< markers
  • Decide which version to keep (or write a combined version)
  • Delete ALL conflict markers (<<<, ===, >>>)
  • Stage the resolved file: git add <file>
  • Complete the merge: git commit
⚠️ Tip: Use VS Code's built-in merge conflict UI — it shows "Accept Current", "Accept Incoming", "Accept Both" buttons. Much easier than editing raw markers manually.
05
Rebase — Alternative to Merge
›

Rebase replays your commits on top of another branch, creating a linear history without merge commits.

# On feature branch, rebase onto latest main
git checkout feature-login
git rebase main

# Interactive rebase — edit, squash, reorder commits
git rebase -i HEAD~3    # last 3 commits
MergeRebase
HistoryPreserves all history (non-linear)Creates clean linear history
Commit IDsOriginal hashes preservedCreates new commit hashes
SafetySafe on shared/public branchesNever rebase shared branches!
Use caseIntegrating team work, PRsCleaning up local commits before PR
🎯 Golden Rule of Rebase: "Never rebase a public branch that others are working on." Rebase rewrites commit hashes — anyone who has the old commits will have a broken history.

Core GitHub Operations
›
Command / ActionWhat it does
git clone <url>Copy a remote repo to your local machine (full history)
git push origin mainUpload your local commits to GitHub

git fetchDownload remote changes but do NOT merge (safer)

🎯 Interview tip: git pull = git fetch + git merge. Use git fetch when you want to inspect remote changes before deciding to merge. Safer for production branches.
02
Pull Requests (PRs)
›

A Pull Request is GitHub's mechanism to propose merging your branch into another. It enables code review, discussion, and automated checks before merging.

Standard PR Workflow

  • Create a branch: git checkout -b feature/navbar
  • Make commits, then push: git push origin feature/navbar
  • On GitHub: click "Compare & pull request"
  • Write a description — what changed and why
  • Request reviewers; address review comments
  • Once approved: merge the PR (Squash / Merge commit / Rebase)
  • Delete the remote branch after merging
✅ Best practice: Keep PRs small and focused. A PR reviewing 1000 file changes is nearly impossible. Aim for PRs that can be reviewed in under 30 minutes.

README, Issues & GitHub Features
›

README.md — First Impression of Your Repo

  • Written in Markdown — the landing page of your GitHub repository
  • Should contain: project name, description, tech stack, installation steps, usage, screenshots, license

Issues — Bug & Task Tracker

Other Key GitHub Features

SSH Keys — Passwordless Auth
› 
# Generate SSH key pair
ssh-keygen -t ed25519 -C "you@email.com"

# Copy public key → add to GitHub Settings > SSH Keys
cat ~/.ssh/id_ed25519.pub

# Test connection
ssh -T git@github.com
Hi username! You've successfully authenticated.

# Switch remote to SSH URL
git remote set-url origin git@github.com:user/repo.git
🎯 Interview tip: SSH uses asymmetric cryptography. Private key stays on your machine; public key given to GitHub. Authentication happens without a password — more secure and convenient for daily development.
